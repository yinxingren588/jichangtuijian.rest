“丢包率1%”如果没有分母、目标和时间窗口，很难复核。先问这个数字来自什么探测、发送多少、等待多久以及丢失集中在哪段。网络层探测与真实业务失败不是同一件事，报告时应分别命名。

## 最少保留这些条件

| 条件 | 示例写法与注意事项 |
| --- | --- |
| 本地环境与目标 | 设备、运营商、接入方式、目标地址或服务类别 |
| 探测方法 | 协议、方向、报文大小、间隔、超时阈值 |
| 分子与分母 | 发送100次，按既定阈值判定1次未达 |
| 时间范围 | 起止时间及时区，是否中断或切换网络 |
| 丢失分布 | 连续丢失长度、发生位置和是否缺测 |

RFC 7680讨论单向IP丢失度量，强调方法和判断条件的重要性。普通ping通常观察往返响应，涉及请求与返回；不能把它直接叫作严格的单向丢包测量，也不能仅凭某个中间节点不响应定位链路故障。

## 同为1%，业务影响可能不同

假设各发送1000次探测，两组都丢10次。一组分散发生，另一组连续丢10次。二者总比例均为1%，但连续中断对会话、音视频和恢复过程的影响可能不同。此处是假设数据，不表示本站测得某条线路丢包。

还要分开“没有发送”和“发送后未收到”。笔记本休眠、工具停止和网络切换期间没有样本，应记录缺测；不能把它们默认为全成功，也不应随意补成全部丢失。不同超时阈值下的结果不宜直接排名。

## 网络探测与应用结果怎样对照

在权限允许范围内，采用适当频率的小规模探测，同时记录真实任务是否失败。若ping受限而网页正常，应保留这一差异；网页失败而探测正常，也可能发生在认证、DNS、TLS或目标应用阶段。分别排查，避免通过单一协议给所有业务下结论。

出现异常时，保持设备与目标不变，记录本地连接状态和其他目标对照；不要为确认结果长时间高频压测。记录完成后先看[ICMP的解释边界](/blog/icmp-limitations/)，再结合[稳定性方法](/blog/stability-method/)分析。本站图表若缺少探测分母和完整环境，应继续标为资料线索，不能补写长期丢包率。
